# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build System

This is an ESP32 embedded firmware project using **PlatformIO**.

```bash
pio run                        # Build
pio run --target upload        # Flash to ESP32
pio device monitor             # Serial monitor (115200 baud)
pio run --target clean         # Clean build artifacts
```

There are no tests or linters — the project has direct hardware dependencies.

## Architecture

This firmware runs on an ESP32 and bridges a camera (DJI Action or GoPro) to a Betaflight flight controller via MSP serial:

```
DJI Action / GoPro Camera ←—BLE—→ ESP32 ←—MSP Serial—→ Betaflight FC
```

### Layers

- **`src/camera.h`** — Abstract `Camera` base class with the shared interface (`begin`, `update`, `isConnected`, `startRecording`, `stopRecording`, `switchCameraMode`) and the `CameraCallback` typedef. Also holds `setRegistry`, `setStrictCamera`, and `setCameraCallback` wiring methods used by `main.cpp`. Both camera implementations inherit from this.

- **`src/ble_camera.cpp`** — `BLECamera : public Camera`. BLE client for DJI Action cameras. Scans for manufacturer ID `0x08AA` / marker `0xFA`, connects, subscribes to GATT notifications on service `0xFFF0` / char `0xFFF4`, writes commands on char `0xFFF5` (or `0xFFF3` on Action 5 Pro). Calls registered callback on every status push.

- **`src/dji_protocol.cpp`** — Encodes/decodes DJI BLE frames. This is DJI's own openly published "R SDK" wire format (confirmed byte-for-byte against `dji-sdk/Osmo-GPS-Controller-Demo`'s `protocol.md`/`protocol_data_segment.md`, which DJI writes only lists as supporting Action 4 / Action 5 Pro / Action 6 / Osmo 360 — Action 2 and 3 predate that published doc, so their exact command-set support is unconfirmed even though the GATT layout is known to match). DJI uses a non-standard CRC-16 (seed `0x3AA3`) for the header and CRC-32 for the payload. Key command IDs: CmdSet `0x00` CmdID `0x19` (connect — the camera's own hello carries a per-model `device_id`, e.g. `0xFF33`/`0xFF44`/`0xFF55`/`0xFF66`, logged by `ble_camera.cpp` on connect), CmdSet `0x1D` CmdID `0x05` (subscribe to status at 2 Hz), CmdSet `0x1D` CmdID `0x02` (status push with battery % and recording state — `video_resolution`/`fps_idx` in that push are sparse per-model codes per the official doc, not sequential indices, so `ble_camera.cpp` maps them with an explicit switch rather than array indexing).

- **`src/gopro_camera.cpp`** — `GoProCamera : public Camera`. BLE client for GoPro cameras (Open GoPro BLE API). Scan (`onResult()`) enables BLE duplicate advertisements and clears scan results before each scan (`scan->setAdvertisedDeviceCallbacks(this, true)` + `scan->clearResults()`) — required so a camera transitioning from sleeping to awake at the same BLE address is seen again rather than suppressed by the stack's dedup, since the wake guard below depends on observing that transition. When `_wakeGuard` (`Camera::setWakeGuard()`, default true) is set, manufacturer-data bytes `[2]`/`[3]` are read as a camera "family"/awake-state pair (derived from real HERO11 Mini and MAX2 traffic: family `0x02` is awake on state `0x01`/`0x05`, family `0x03` is awake only on `0x01`); a camera that's known-asleep or an unrecognized family is logged but not auto-connected, preventing the ESP32 from waking a powered-down camera via GATT connection. This filter is bypassed for a camera the user explicitly selected (`_registry->hasSelection()` and its address matches `preferredAddr()`), since that's explicit intent to connect regardless of state. Scans for service UUID `0xFEA6`, subscribes to GP-0073 (command ack) and GP-0077 (status notify), performs the hardware-info handshake, then registers for push notifications on battery %, encoding state, recording duration, SD remaining, overheating, and preset group. Push notifications (`0x92`/`0x93`) carry the same leading status byte as query-ack responses (`0x52`/`0x53`) — confirmed against real hardware traffic — so both are parsed by skipping 2 header bytes before the TLV body. `switchCameraMode` maps DJI_MODE_* constants to GoPro preset groups. `triggerBurstSloMo` / `exitBurstSloMo` change the sub-mode setting without switching preset groups (used by the AUX switch when already recording). Older cameras that predate the preset-group scheme (e.g. HERO4/5 Session) ack the modern status-ID registration but silently never push values for the modern-only IDs (encoding=10, preset group=96) — confirmed on real HERO5 Session hardware — so the status registration always requests the *union* of modern and legacy IDs (recording=8, mode=43 alongside the modern set; see `gopro_protocol.h`) rather than picking one; unsupported IDs in the batch are just never pushed. If the whole batch is rejected outright (`status != 0`), `_legacyProtocol` is set and the connection retries once with the legacy-only ID set, and `switchCameraMode` then uses the plain capture-mode command (`0x02`) instead of preset groups. SD-remaining (status ID 54) arrives as a uint32 MB value on modern cameras but a uint64 KB value on HERO4/5-Session-era firmware — both widths are handled. If a queried setting ID is unsupported (e.g. HyperSmooth, HERO7+), that registration is skipped rather than blocking readiness — extended setting telemetry (resolution/fps/EIS) is just unavailable, same as a legacy status-ID rejection after the retry: the camera is still marked ready for record/mode commands, just without telemetry. Separately, best-effort discovers the standard Bluetooth SIG Battery Service (`0x180F`) and subscribes to Battery Level (`0x2A19`) — confirmed on real HERO5 Session hardware that battery % is reported there instead of via status ID 70 on the FEA6 TLV channel (that field comes back zero-length on that generation); a missing service/characteristic just means no battery telemetry from this path, not a connection failure, and modern cameras that do push a value via status ID 70 are unaffected.

- **`src/gopro_protocol.h`** — GoPro BLE constants (service/char UUIDs, command IDs, status IDs) and the `GpRxAssembler` struct for reassembling multi-packet BLE messages. Also holds the legacy HERO4/5-Session-era protocol constants (`GP_CMD_LEGACY_SET_CAPTURE_MODE`, `GP_STATUS_LEGACY_RECORDING`, `GP_STATUS_LEGACY_MODE`) registered alongside the modern IDs by `gopro_camera.cpp`, with the legacy-only set used as a fallback if the combined registration is rejected outright.

- **`src/sony_camera.cpp`** — `SonyCamera : public Camera`. BLE client for Sony Alpha cameras, implementing two of Sony's undocumented BLE services (see `sony_protocol.h`; reverse-engineered by the [freemote](https://github.com/coral/freemote) project and [rock3r/CameraSync](https://github.com/rock3r/CameraSync)'s protocol docs). Scans for manufacturer ID `0x012D` / device type `0x0300`, connects, then requests an encrypted+bonded link via `esp_ble_set_encryption()` — the camera rejects writes/notifications until bonded (Just Works pairing; first-time pairing requires the camera's Bluetooth Rmt Ctrl menu to be open). Implements `BLESecurityCallbacks`; once `onAuthenticationComplete()` reports success, discovers the "Remote Control" service `8000FF00`, subscribes to notify char `0xFF02`, and writes button commands to `0xFF01`. Recording start/stop both send the same record-button down/up toggle (`0x0F` then `0x0E`), guarded by last-known recording state since the protocol has no explicit start/stop command. `switchCameraMode` is unsupported (no mode-switch command exists in this protocol) and always returns false. Separately, best-effort discovers the "Camera Control" service `8000CC00` and subscribes to battery notify char `0xCC10` (some models reduce/disable this service while Bluetooth Rmt Ctrl is active — a missing service just means no battery telemetry, not a connection failure). No resolution/fps/EIS/storage telemetry is available from either service — only focus/shutter/recording state and battery %.

- **`src/sony_protocol.h`** — Sony BLE remote constants (service/characteristic UUIDs, manufacturer-data scan prefix, button command codes, notification tag codes).

- **`src/blackmagic_camera.cpp`** — `BlackmagicCamera : public Camera`. BLE client for Blackmagic Design cameras (Pocket Cinema Camera, URSA, Studio range), implementing the Blackmagic Camera Control Protocol over BLE (see `blackmagic_protocol.h`; this is the same "SDI Camera Control Protocol" the cameras also speak over the video cable, re-exposed as BLE GATT characteristics — official Blackmagic Design developer PDF, cross-checked against coral/blackmagic-camera-control, coral/blackmagic-camera-protocol, schoolpost/BlueMagic32, and marklysze/Magic-Pocket-Control-ESP32). Scans for the advertised Blackmagic Camera Service UUID `291d567a-...`, connects, reads the Protocol Version and writes the device name (both plaintext), then subscribes to Incoming Camera Control and Camera Status — both marked "encrypted" in the protocol doc, so the first subscribe auto-triggers bonding. The camera shows a 6-digit PIN on its own screen and expects it typed back in; since the ESP32 has no display/keypad, `onPassKeyRequest()` blocks reading digits from the debug serial console (same approach as BlueMagic32/Magic-Pocket-Control-ESP32) — this only happens once per bond, not on every reconnect. Recording start/stop sends a Transport Mode "assign value" command (category 10, parameter 1: 0=Preview, 1=Play, 2=Record) on Outgoing Camera Control; the camera echoes the same message back on Incoming Camera Control, which is how recording state is tracked. `switchCameraMode` is unsupported (no mode-switch command exists in this protocol) and always returns false. No battery, resolution, fps, or EIS telemetry is exposed over BLE for this camera family — those `CameraData` fields stay at their defaults (EIS explicitly marked unknown).

- **`src/blackmagic_protocol.h`** — Blackmagic BLE service/characteristic UUIDs, the Camera Status flag bits, and the SDI/Bluetooth Camera Control Protocol packet framing (destination/length/command-id/reserved header, category/parameter/data-type/operation command, zero-padded to a 4-byte boundary) plus a helper to build the Transport Mode command used for recording control.

- **`src/insta360_camera.cpp`** — `Insta360Camera : public Camera`. BLE client for Insta360 action cameras (X3, X4, ONE R/RS, GO 2/3, etc.), speaking the same simple BLE command channel the official phone app uses (service `0xBE80`; see `insta360_protocol.h` — cross-checked between real captured traffic from a Hackaday.io writeup and Insta360's own packet-format developer docs, both agreeing byte-for-byte on the header layout). Unlike DJI/GoPro (manufacturer ID) or Blackmagic (dedicated advertised service), there's no verified vendor scan filter for this family, so `onResult()` identifies candidates by the advertised service UUID `0xBE80` where present, falling back to a best-effort check of the advertised local name against known model prefixes ("X3", "GO 3", etc.) — neither signal is guaranteed, but the registry's saved address takes over on every reconnect after the first successful pairing regardless. No bonding/encryption is required by this protocol (unlike Sony/Blackmagic). Recording start/stop send a Phone Command (start/stop video) and only update `CameraData.recording` once the camera's 200-OK ack for that specific command arrives — the response's protobuf body (actual camera-pushed recording/battery/mode state) has no publicly available schema to decode (it's Protocol Buffers extracted from the official app's `libOne.so`), so nothing else is parsed from it. `switchCameraMode` is unsupported: the protocol only exposes separate "start recording in mode X" commands (HDR/bullet/timeshift/loop) rather than a stateless mode-switch, and only the "start video normal" variant is verified here. Separately, best-effort discovers the standard Bluetooth SIG Battery Service (`0x180F`) / Battery Level (`0x2A19`) for battery %, since it isn't part of the documented `0xBE80` channel — a missing service just means no battery telemetry, not a connection failure. No resolution/fps/EIS telemetry is available at all (EIS explicitly marked unknown).

- **`src/insta360_protocol.h`** — Insta360 BLE service/characteristic UUIDs (`0xBE80`/`0xBE81`/`0xBE82`), the Phone Command packet framing (length/message-type/command-code/sequence-number header, no protobuf payload for the commands sent here), the `0x0003`/`0x0004`/`0x0005` (photo/start-video/stop-video) command codes, and a helper to build a command packet.

- **`src/msp_serial.cpp`** — MSP v2 protocol over UART. Polls `MSP_STATUS` (cmd 101) every 100 ms to detect arm state (bit 0 of flight mode flags bytes 6–9). Sends telemetry to Betaflight:
  - `MSP2_CAMERA_BATTERY` (`0x3001`): voltage, current, capacity, temperature
  - `MSP2_SET_TEXT` Custom Messages 1–4 via `sendCustomOSD1`–`sendCustomOSD4`, each delegating to the private `sendCustomOSD(textType, data, tpl)` helper. The helper expands a user-configurable template string using `expandTemplate()` and `resolveToken()`. Supported tokens: `{bat}`, `{rec}`, `{mode}`, `{res}`, `{fps}`, `{eis}`, `{rleft}`, `{rcap}`. Default templates reproduce the original hardcoded formats.
  - `MSP2_SET_TEXT` Pilot Name / Craft Name via `sendPilotName`/`sendCraftName` (also delegating to `sendCustomOSD`, with text type `MSP_TEXT_PILOT_NAME`=1 / `MSP_TEXT_CRAFT_NAME`=2) — an alternate telemetry path for Betaflight 4.5, which has these two text fields but not the Custom Message 1-4 fields added in 4.6. `main.cpp` only calls these two (instead of `sendCustomOSD1`–`4`) when the `bf45Compat` config flag is set.

- **`src/main.cpp`** — Wires the layers together. Selects the active camera (`BLECamera`, `GoProCamera`, `CaddxCamera`, `SonyCamera`, `BlackmagicCamera`, or `Insta360Camera`) at startup based on the `cameraType` NVS config, then uses it via the `Camera*` interface. On arm state change, triggers camera recording start/stop. Re-sends telemetry on battery update or keepalive timeout, sending either the four `osdN` Custom Messages or, when `bf45Compat` is enabled, Pilot Name/Craft Name via `pilotNameTpl`/`craftNameTpl` — never both, since BF4.5 doesn't have the Custom Message fields to receive the former. AUX switch: when GoPro is active and recording, high/low triggers `triggerBurstSloMo` / `exitBurstSloMo`; otherwise calls `switchCameraMode` with the configured `auxMode`.

- **`src/camera_registry.cpp`** — Persists a list of up to 64 previously connected cameras in NVS namespace `cam_reg`. Each entry stores name, BLE address, address type, and camera type (DJI/GoPro). On startup every BLE-scanning camera implementation (`BLECamera`, `GoProCamera`, `SonyCamera`, `BlackmagicCamera`, `Insta360Camera`) queries the registry for the preferred address (last connected, or manually selected via `cameras connect <idx>`) and applies it per the shared `_matchMode` (`CAM_MATCH_*` in `camera.h`, set via `Camera::setMatchMode()`): `CAM_MATCH_FALLBACK` (default) stops the scan early on the preferred address and otherwise falls back to the first eligible camera found once the scan window ends; `CAM_MATCH_STRICT` never falls back — only the preferred address is accepted; `CAM_MATCH_BEST_SIGNAL` ignores the preferred address entirely, lets the scan run its full window tracking the strongest-RSSI eligible camera seen (`_bestAddr`/`_bestRssi`), and connects to that one. `hasSelection()` marks an explicit `cameras connect <idx>` / hosted-UI selection, which `GoProCamera`'s wake guard (see below) treats as intent that overrides its own filtering. `onConnected()` is called after every successful BLE connection to update the list and mark the last-connected entry.

- **`src/config_manager.cpp`** — Runtime configuration via NVS. Parses serial commands (`help`, `show`, `set <key> <val>`, `reset`, `cameras list/connect/remove/clear`). Persisted keys: `camera_type` (0=DJI, 1=GoPro, 2=Caddx Orca, 3=Sony, 4=Blackmagic, 5=Insta360), `cam_match` (`CAM_MATCH_*` from `camera.h` — see `src/camera_registry.cpp` entry above), `wake_guard` (default true — see `src/gopro_camera.cpp` entry above), `disarm_delay`, `stop_on_disarm`, `aux_channel`, `aux_mode` (default `0x00` = slow motion), `osd1_tpl`–`osd4_tpl` (OSD template strings, defaults reproduce the original hardcoded formats), `bf45_compat` (default false — see `src/msp_serial.cpp` entry above), `pilot_tpl`/`craft_tpl` (Pilot Name/Craft Name templates, only sent when `bf45_compat` is true; defaults `CAM:{bat}`/`{rec}`), `wifi_ap_en` (default true — false disables auto-starting the config-portal AP entirely; the BOOT-button force-AP hold in `main.cpp` bypasses this), `wifi_ap_delay` (seconds after boot/camera-disconnect before the AP auto-starts, default 30 — replaces the old compile-time `WIFI_AP_START_DELAY_MS`).

- **`src/telemetry.h`** — Shared `CameraData` struct used by both camera implementations and MSP output.

- **`include/config.h`** — Compile-time constants: GPIO pins, baud rates, scan duration, reconnect delay, keepalive intervals.

### Key design patterns

- `BLECamera`, `GoProCamera`, and `SonyCamera` each use a static singleton (`_instance`) for BLE stack callbacks (trampoline pattern). Only one is active at a time.
- BLE writes must not happen inside a notify callback — both camera classes defer writes to their `update()` method using pending-action flags.
- All DJI wire-format structs use `__attribute__((packed))` for direct serialization.
- `MSPSerial` parses incoming bytes with an explicit state machine.
- GoPro uses TLV-encoded commands and registers for status push notifications rather than polling. Responses may span multiple 20-byte BLE packets; `GpRxAssembler` handles reassembly.
